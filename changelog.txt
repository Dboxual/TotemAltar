[1.1.24] — 2026-06-16
----------------------
ADDED: Dormant Bedrock Relic can now naturally generate in Ancient City,
Nether Fortress, and Stronghold chests, in addition to the existing Bastion
Remnant chest drop.

  BedrockRelicLootListener now resolves a per-structure chance from config
  based on the vanilla loot table key:
    - minecraft:chests/bastion_*        -> bedrock-relic.spawn-chance
    - minecraft:chests/ancient_city*    -> bedrock-relic.ancient-city-chance
    - minecraft:chests/nether_bridge    -> bedrock-relic.nether-fortress-chance
    - minecraft:chests/stronghold_*     -> bedrock-relic.stronghold-chance

  Each chest independently rolls its configured chance via LootGenerateEvent,
  so this works for naturally generated structures (no per-structure code
  needed beyond the loot table key match). The item dropped is always the
  dormant (non-activated) Bedrock Relic produced by ItemUtil.createBedrockRelic(),
  which already carries the BEDROCK_RELIC_KEY PDC tag the altar/activation flow
  expects — never the finished BedRocker pickaxe.

  Default chances (all configurable in config.yml under bedrock-relic:):
    ancient-city-chance:     0.02  (2%)
    nether-fortress-chance:  0.02  (2%)
    stronghold-chance:       0.015 (1.5%)

[1.1.23] — 2026-06-13
----------------------
CHANGED: Shard kill progress now only counts when the shard is held in the offhand.

  Previous behaviour:
    AffinityListener scanned the offhand first, then fell through to scan slots
    0–8 (the hotbar) if no shard was found in the offhand. This meant kills could
    accumulate on a shard sitting anywhere in the hotbar, not just the offhand.

  New behaviour:
    Only the offhand slot is checked. If no valid unmorphed Totem Shard is in the
    offhand, the kill is ignored for shard progression. Hotbar scanning removed.

  Also updated:
    - Guide book text updated from "Keep one in your hotbar" to
      "Hold one in your offhand" to match the new requirement.

[1.1.20] — 2026-06-12
----------------------
FIXED: Shadow Totem no longer reveals a burning player via visible fire.

  Root cause:
    Setting a player invisible hides their model but NOT their fire ticks.
    A player burning from Fire Aspect, lava, flame arrows, or any other source
    would still display visible flames to nearby players even while the Shadow
    Totem invisibility was active, negating stealth.

  Fix — three-layer approach:

    1. Extinguish on activation (TotemActivationListener.doShadow):
       player.setFireTicks(0) is called immediately when the totem pops,
       before the INVISIBILITY effect and ShadowArmorManager.startShadow().
       Any active burn is cleared at the instant of activation.

    2. Cancel re-ignition during shadow (ShadowArmorManager, EntityCombustEvent):
       A HIGH-priority EntityCombustEvent handler cancels all combustion events
       (fire aspect, lava, flame arrows, campfires, etc.) for any player currently
       in shadow. The player cannot be set on fire again while stealth is active.

    3. Periodic enforcement (ShadowArmorManager, enforceAllShadows):
       The existing 1-second enforcement task that re-sends empty armor packets
       now also resets fire ticks to 0 for each shadow player who has them.
       This covers edge cases where combustion fires before the event handler.

  Scope:
    EntityCombustEvent suppression also prevents fire damage during shadow,
    which is consistent with the intent: full stealth and concealment.
    No other totem or mechanic is affected.

  Confirmed clean from previous audit:
    Shadow Totem has no FLAME or FIRE particles (only SMOKE at activation).
    No arrow or projectile effects exist in doShadow or ShadowArmorManager.

FILES: TotemActivationListener.java,
       ShadowArmorManager.java,
       plugin.yml, build.gradle.kts,
       changelog.txt, chatgpt.txt

[1.1.19] — 2026-06-12
----------------------
FIXED: Bedrock Relic items placed as blocks no longer lose their plugin data.

  Root cause:
    The Bedrock Relic and Activated Bedrock Relic items use GILDED_BLACKSTONE as
    their base material, which is a fully placeable vanilla block. When a player
    placed the item, Minecraft created a standard GILDED_BLACKSTONE block with no
    way to attach PDC data (GILDED_BLACKSTONE has no TileState). On break, the
    block dropped as a plain GILDED_BLACKSTONE item with no relic PDC tags.

  Solution — plugin-side coordinate storage:
    A new BedrockRelicBlockManager stores a persistent map of placed relic block
    locations in bedrock_relic_blocks.yml (world:x:y:z → activated status).
    The map survives plugin restarts; entries are removed when blocks are broken.

  BlockPlaceEvent (BedrockRelicPlacementListener):
    When a Bedrock Relic or Activated Bedrock Relic item is placed, the block
    location and activated state are registered in BedrockRelicBlockManager.

  BlockBreakEvent:
    When a registered relic block is broken:
      - Vanilla drops are suppressed (setDropItems false, setExpToDrop 0).
      - The correct relic variant (inactive or activated) is dropped as a
        naturally-falling item at the block position.
      - In creative mode the block is removed without any drop (matches vanilla
        creative behavior).

  EntityExplodeEvent / BlockExplodeEvent:
    Relic blocks in explosion block lists are removed from the list (preventing
    vanilla TNT/creeper drops), destroyed manually (setType AIR), and the proper
    relic item is always dropped — exactly one item, no duplication.

  BlockPistonExtendEvent / BlockPistonRetractEvent:
    Pistons cannot push or pull tracked relic blocks. The event is cancelled to
    prevent coordinate desync between the block position and the storage map.

       ItemUtil.java (createRelicDrop helper),
       TotemAltars.java,

[1.1.18] — 2026-06-12
----------------------
CHANGED: Swap Totem now targets nearby mobs in addition to players.

  Previously the Swap Totem only swapped the user with another online player.
  It now builds a shared pool of all valid targets — players AND living mobs —
  and picks one at random with equal probability.

  Target selection:
    - Collects all valid players within 25 blocks first, then all valid living
      mobs within 25 blocks, into one flat list.
    - Picks a single target with ThreadLocalRandom — uniform distribution across
      the entire pool (e.g. 1 player + 9 mobs = 10 candidates each at 1/10 odds).
    - Distance does NOT affect selection weight. The closest entity is not
      preferred. The entity in front of the player is not preferred.

  Valid mob targets:
    - Any LivingEntity that is not a Player, not an ArmorStand, not dead, and
      does not have a custom name / nametag set.
    - Named entities (name-tagged pets, villagers, quest mobs, named altar mobs,
      etc.) are excluded entirely — this prevents accidental swaps with
      intentionally preserved mobs.

  Valid player targets (unchanged):
    - Online, non-spectator players within 25 blocks, excluding self.

  Fallback (unchanged):
    - If no valid targets exist the existing "swap-no-target" message is shown.

  Swap mechanics (unchanged):
    - Locations are exchanged, yaw/pitch preserved for each party.
    - Existing particles, sounds, messages, and cooldowns are all unchanged.
    - The action-bar notification ("You were swapped by X!") is now only sent
      when the target is a Player (mobs don't have action bars).

FILES: TotemActivationListener.java,
       plugin.yml, build.gradle.kts,
       changelog.txt, chatgpt.txt

[1.1.17] — 2026-06-12
----------------------
FIXED: Shadow Totem no longer leaks armor to nearby players while stealth is active.

  The prior implementation applied Invisibility but did not hide the player's
  equipped armor from other clients. Nearby players could still see the hidden
  player's armor pieces even while fully invisible.

  Solution — packet-level fake equipment:
    - On shadow start: sends fake AIR equipment for helmet/chestplate/leggings/boots
      to every online viewer (packet-only; the hidden player's real inventory is
      untouched throughout).
    - On shadow end: sends the player's real equipment back to every online viewer
      so armor reappears instantly without any desync.
    - Held items are unaffected (follows existing intended design — not hidden).

  Edge cases handled:
    - Player joins while someone is hidden → PlayerJoinEvent sends fake equipment
      for all active shadows to the newcomer.
    - Player changes armor while hidden → PlayerArmorChangeEvent re-enforces fake
      empty armor on the next tick (avoids a brief flash of real armor).
    - Plugin disable → real equipment restored to all viewers before state is cleared.
    - A periodic 1-second enforcement task re-sends empty armor to all viewers,
      covering players who enter render range while someone is hidden.

  Implementation: ShadowArmorManager now uses Paper API
  Player#sendEquipmentChange(LivingEntity, Map<EquipmentSlot, ItemStack>) —
  no external packet library required.

ADDED: Admin command to give a pre-repaired (finished) altar item.

  /totemaltars givefinishedaltar <player> [amount]

  - Gives an ANVIL-based altar item with the standard totemaltars:totem_altar
    PDC tag plus a new totemaltars:totem_altar_active PDC flag.
  - When placed, the altar skips the repair ritual and registers immediately
    at stage=1 (active/repaired) — hologram shows "✦ INSERT SHARD ✦" straight away.
  - All subsequent forging steps (shard insert → totem insert → claim) work
    identically to a normally repaired altar.
  - Item name, enchant glow, and PDC tag are consistent with givealtar.
  - Amount clamped 1–64, defaults to 1. Overflow drops at player's feet.
  - Tab completion: arg 1 = online player names, arg 2 = amounts (same as givealtar).
  - Permission: totemaltars.admin.

FILES: ShadowArmorManager.java,
       ItemUtil.java,
       AltarPlacementListener.java,
       TotemAltarsCommand.java,
       config.yml, plugin.yml, build.gradle.kts,
       changelog.txt, chatgpt.txt

  ────────────────────────────────────
  Step 1 — Find a Bedrock Relic in a Bastion Remnant chest.

    Right-click any Bedrock block while holding the inactive relic.

      Slot 15: place Netherite Pickaxe

    Every Totem Shard now carries a unique UUID in its PDC under the key
    totemaltars:shard_uuid. Since Minecraft only stacks items with identical NBT,
    this guarantees each shard is a distinct, non-stackable item.

    createShard(): UUID written into the initial PDC block (one setItemMeta pass).
    ensureShardUuid(ItemStack): new public method — assigns UUID only if absent,
      never overwrites. Called lazily from updateShardLore() and morphShard() so
      all old shards get a UUID the next time they receive any affinity progress.
    Old Echo Shard or Amethyst Shard-based shards with no UUID are safe — their
    affinity, lore, and type data are untouched; they simply gain the UUID tag.

[1.1.8] — 2026-06-10
---------------------
CHANGED: Forged totem is now claimed from the altar, not given directly to inventory.

  Previously, right-clicking the altar with a vanilla Totem of Undying immediately
  gave the forged typed totem to the player's inventory, with a 5-second visual
  display that simply despawned.

  New behaviour (three-stage forge):
    1. Insert morphed shard → altar enters stage=2 (awaiting totem).
       Shard ItemDisplay floats above altar.

    2. Right-click with vanilla Totem of Undying → totem consumed, effects fire
       (lightning, TOTEM particles, beacon sound), altar enters stage=3 (totem ready).
       Shard display is replaced by a persistent Totem of Undying ItemDisplay.
       Hologram shows "✦ CLAIM YOUR TOTEM ✦".
       Player receives message: forge-totem-ready.

    3. Right-click altar (no item required) → player claims the forged totem.
       Display removed, pickup sound plays, altar resets to active (stage=1).
       Player receives message: forge-complete.

  Anti-duplication / ownership:
    - The inserting player's UUID is stored as the altar owner at shard insertion.
    - Only the owning player can claim the totem; others see "forge-wrong-owner".
    - forgingInProgress lock prevents double-claim from spam clicks.
    - Stage=3 persists in altars.yml across server restarts; Totem display is
      restored on chunk load.

FILES: AltarManager.java, AltarEffectsManager.java, AltarInteractionListener.java,
       ConfigManager.java, config.yml, build.gradle.kts, plugin.yml

[1.1.6] — 2026-06-09
---------------------
ADDED: Two-step altar forging flow.

  Previously, inserting a morphed Totem Shard directly yielded a forged totem.
  Now the shard is the first step and a Totem of Undying is required to complete
  the forge.

  New flow:
    1. Right-click active altar → Forging GUI → insert morphed shard
       → shard consumed, altar enters "awaiting totem" state
       → floating Totem of Undying ItemDisplay appears above altar
       → hologram updates to "⚡ INSERT TOTEM ⚡"
       → message: forge-insert-totem

    2. Right-click altar with vanilla Totem of Undying in main hand
       → 1 Totem consumed, completion effects (lightning, particles, sound)
       → forged typed totem given to player
       → ItemDisplay removed, hologram reverts to active text
       → message: forge-complete

  Behaviour:
    - Only a vanilla (non-custom) Totem of Undying is accepted in step 2.
    - Stage=2 (awaiting totem) is persisted in altars.yml and survives restarts.
    - Totem display and hologram are restored on chunk load.
    - Anti-double-click guard prevents duplicate forging from spam clicks.
    - Off-hand interactions are ignored; main hand only.

FILES: AltarManager.java, AltarEffectsManager.java, AltarInteractionListener.java,
       ConfigManager.java, config.yml, plugin.yml, build.gradle.kts
