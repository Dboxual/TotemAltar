PURPOSE
  Entry point; extends JavaPlugin. Bootstraps every subsystem.

MAIN RESPONSIBILITIES
  • Instantiates all managers in dependency order on onEnable().
  • Registers all 8 listeners + the AltarEffectsManager (which is also a
    Listener for ChunkLoadEvent) with the server plugin manager.
  • Registers the shaped crafting recipe for the Totem Altar item.
  • Wires /totemaltars command executor and tab-completer.
  • Calls altarEffectsManager.start() to launch the idle particle scheduler
    and restores holograms on tick 1.
  • On onDisable(): gracefully shuts down effects, shadow manager, and ritual
    manager.

COMMANDS
  Registers a single root command: /totemaltars (delegated to
  TotemAltarsCommand).

LISTENERS  (registered here)
  MobDropListener, AffinityListener, AltarPlacementListener,
  AltarInteractionListener, RitualListener, TotemActivationListener,
  GuardianListener, LegacyIngredientDropListener, AltarEffectsManager.

CONFIG OPTIONS USED
  Via ConfigManager: altar.recipe.shape, altar.recipe.ingredients. Falls back
  to a hard-coded default recipe (OOO / DED / ONO with OBSIDIAN, DIAMOND,
  ECHO_SHARD, NETHER_STAR) if config is missing or invalid.

DATA STORAGE
  None directly. All data is owned by the managers it holds.

KNOWN TODOS / ISSUES
  • isRecipeConfigValid() rejects configs where any non-space character has no
    ingredient mapping — this is correct but is not communicated well to the
    server operator beyond a warning log.
  • The log line "[recipe] result: ... ECHO_SHARD (not a custom Totem Shard)"
    indicates a potential player confusion point that was noticed by the
    developer but not yet resolved in UI/documentation.

PURPOSE
  Tracks player mob kills and applies affinity progress to Totem Shards.

MAIN RESPONSIBILITIES
  • Listens for EntityDeathEvent at MONITOR priority (ignoreCancelled=true).
  • Looks up the killed entity's type in the mob-affinity cache.
  • Searches killer's offhand first, then hotbar slots 0–8, for the first
    unmorphed Totem Shard.
  • Calls itemUtil.addAffinity() (+1) and checks all AFFINITY_TYPES against
    threshold; morphs on first match.

COMMANDS
  None.

LISTENERS
  EntityDeathEvent (MONITOR, ignoreCancelled=true).

  affinity.mob-types (via ConfigManager.getAffinityTypeForMob),
  affinity.threshold.

DATA STORAGE
  PDC on the ItemStack: affinity_blast, affinity_shadow, affinity_storm,
  affinity_guardian, affinity_swap (all INTEGER).

KNOWN TODOS / ISSUES
  • Only the FIRST unmorphed shard in offhand → hotbar is updated. If a player
    has multiple shards, the others receive no affinity.
  • Morphing checks AFFINITY_TYPES in list order (blast first). If two
    affinities simultaneously reach threshold, only the first in the static
    list triggers — the second is silently ignored.
  • No visual/audio feedback is played when an affinity point is added.
  • No feedback when a shard morphs (the lore changes but no sound/particle).

PURPOSE
  Drives the two custom GUIs: Altar Repair (insert Wither Skull) and Altar
  Forging (insert morphed shard to produce a totem).

MAIN RESPONSIBILITIES
  • Intercepts RIGHT_CLICK_BLOCK on DAMAGED_ANVIL or ANVIL blocks that are
    registered altars.
  • Inactive altar → opens "Altar Repair" 27-slot GUI (center slot open).
  • Active altar → opens "Altar Forging" 27-slot GUI (center slot open).
  • A ritual-in-progress check blocks opening Repair GUI during an active
    ritual.
  • On click in slot 13 (center): defers 1 tick, then checks what was placed.
    - Repair: requires WITHER_SKELETON_SKULL → starts ritual via
      RitualManager.startRitual().
    - Forging: requires a morphed shard (getShardType != null) → calls
      itemUtil.createForgedTotem() and gives the resulting totem. Any non-shard
      item is returned to the player.
  • All non-center slots in both GUIs are cancelled clicks.
  • Shift-click from player inventory into either GUI is cancelled.
  • On inventory close: item in slot 13 is returned to player inventory.
  • Separate UUID→Location and UUID→Inventory maps for both GUI types prevent
    re-opening if already open.

COMMANDS
  None.

LISTENERS
  PlayerInteractEvent (HIGH, ignoreCancelled=true),
  InventoryClickEvent (HIGH),
  InventoryCloseEvent (NORMAL).

CONFIG OPTIONS USED
  messages.forge-success, messages.ritual-already-active.

DATA STORAGE
  In-memory: repairGUILocs, repairGUIInvs, forgingGUILocs, forgingGUIInvs
  (all transient, keyed by player UUID).

KNOWN TODOS / ISSUES
  • The Repair GUI has no lore/instructions shown to the player — they must
    know from external documentation that a Wither Skull is required.
  • Non-shard items placed in the Forging GUI are returned silently with no
    message explaining why they were rejected.
  • No altar-type binding check in the forging flow. Any active altar accepts
    any morphed shard type. Config messages altar-already-bound, altar-not-bound,
    altar-requires-morphed-shard, and altar-bound-success exist but are NEVER
    sent from any current code path — the binding system is unimplemented.
  • No ingredient slot in the forging GUI — the ingredient system drops
    ingredients into the world but nothing consumes them here.
  • Race condition: two players at the same altar simultaneously could both
    pass the isRitualActive check before either starts a ritual; startRitual()
    does re-check, but the window exists.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PURPOSE
  Intercepts the vanilla totem-of-undying activation (EntityResurrectEvent)
  to trigger custom abilities for the five totem types.

MAIN RESPONSIBILITIES
  • Listens for EntityResurrectEvent (HIGH). Ignores non-player and non-custom-
    totem activations.
  • Reads totem type from PDC on the consumed item (offhand checked first,
    then mainhand).
  • Checks global cooldown (__global__ key). If on cooldown, sends action-bar
    message and returns without triggering.
  • On successful trigger: sets global cooldown, starts per-tick cooldown
    display via action-bar BukkitRunnable, then schedules ability execution
    1 tick later.
  • PlayerQuitEvent: cancels cooldown display task and removes cooldown entry.

  Abilities (all called on tick+1 after resurrection):
  BLAST:   Applies velocity (knockback) to all LivingEntities within radius.
           Spawns EXPLOSION_EMITTER (x3) + FLAME (x30) particles, plays
           ENTITY_GENERIC_EXPLODE sound.
  SHADOW:  Adds INVISIBILITY potion effect for duration * 20 ticks.
           Calls ShadowArmorManager.startShadow() for cleanup tracking.
           Spawns SMOKE particles, plays ENTITY_ENDERMAN_TELEPORT (low pitch).
  STORM:   Calls findSafeLocation() (up to 50 random angle attempts on
           getHighestBlockYAt). Teleports player if found. Spawns PORTAL
           particles at both locations, plays ENTITY_LIGHTNING_BOLT_THUNDER.
  SWAP:    Finds all nearby non-spectator players within range, picks one at
           random. Teleports both (each keeps their own yaw/pitch).
           Spawns PORTAL particles + ENTITY_ENDERMAN_TELEPORT at both spots.
           Sends action-bar notification to the swapped target.
  GUARDIAN:Finds the online ally with matching link UUID, removes their linked
           Guardian Totem, teleports them to the activating player's location.
           Both totems are consumed (activating player's by vanilla, ally's by
           removeTotemWithLinkId).

COMMANDS
  None.

LISTENERS
  EntityResurrectEvent (HIGH),
  PlayerQuitEvent.

CONFIG OPTIONS USED
  global-cooldown, abilities.blast.radius, abilities.blast.knockback-strength,
  abilities.shadow.duration-seconds, abilities.storm.min-distance,
  abilities.storm.max-distance, abilities.storm.max-attempts,
  abilities.swap.range, all messages.* for ability feedback.

    swap     — Player position exchange with nearby random target
    guardian — Pull linked ally to your location on death
  Note: "altar type" (binding a specific altar to one shard type) exists only
  as data fields in AltarManager — the feature is NOT activated. Any active
  altar can forge any morphed shard type.

CURRENT SHARD SYSTEM IMPLEMENTATION
  1. Any Monster killed by a player → 5% chance Totem Shard drops.
  2. Shard is ECHO_SHARD with PDC key totem_shard=1 + five affinity integer
     counters all initialized to 0.
  3. Player kills a mob matching affinity.mob-types config while holding the
     shard in offhand or hotbar (slots 0–8) → +1 to that affinity counter.
  4. When any affinity counter reaches threshold (default 10), shard morphs:
       name changes to "<Type>-Touched Shard"
       lore changes to flavor text
       SHARD_TYPE_KEY set in PDC
  5. Morphed shard can be inserted into an active altar's Forging GUI to
     produce the corresponding Totem of Undying.

CURRENT RITUAL IMPLEMENTATION
  1. Player places Totem Altar (DAMAGED_ANVIL with PDC).
  2. Player right-clicks altar → "Altar Repair" GUI opens.
  3. Player places a Wither Skull in center slot → ritual starts.
  4. Repeating task (every spawn-interval-ticks) spawns up to max-alive-mobs
     from the mob pool around the altar (random angle, radius ring, surface Y).
     Vex have a secondary chance roll and per-type cap.
  5. Each ritual mob is tagged with ritual_mob PDC byte + ritual_altar PDC string.
  6. Each tagged mob kill increments currentKills, updates boss bar (owner only)
     and hologram (all nearby).
  7. At required-kills: cleanup, setActive, DAMAGED_ANVIL → ANVIL block type,
     lightning effect, broadcast "altar-restored".

GAMEPLAY FLOW (complete end-to-end)
  CRAFT ALTAR:
    9 materials in a 3×3 grid (default: OBSIDIAN, DIAMOND, ECHO_SHARD,
    NETHER_STAR) → Totem Altar item (DAMAGED_ANVIL).

  OBTAIN SHARD:
    Kill any hostile Monster → 5% drop chance for Totem Shard.

  MORPH SHARD:
    Hold Totem Shard in offhand or hotbar. Kill mobs matching the affinity
    config (e.g., 10 Creepers for Blast, 10 Wardens for Guardian). After
    threshold kills the shard morphs into a typed shard.

  REPAIR ALTAR:
    Place Totem Altar in world (DAMAGED_ANVIL appears, hologram spawns).
    Right-click the altar → Repair GUI.
    Insert Wither Skull → ritual begins.
    Kill 25 ritual mobs → altar converts to ANVIL (ACTIVE), hologram updates.

  FORGE TOTEM:
    Right-click ACTIVE altar → Forging GUI.
    Insert morphed shard → receive Totem of Undying with type-specific PDC.

  ACTIVATE TOTEM:
    Hold the custom Totem of Undying (main or off hand). Die.
    Vanilla survival resurrection triggers → custom ability fires:
      Blast: knockback ring, explosion particles.
      Shadow: invisibility for 15s, smoke particles.
      Storm: teleport 25–35 blocks to random safe surface location.
      Swap: teleport positions with a random nearby player.
      Guardian: (requires prior linking) pull linked ally to you.
    15-second global cooldown shown in action bar.

  GUARDIAN LINKING (prerequisite for Guardian ability):
    Forge Guardian Totem. While holding it in main hand, right-click another
    online player. Both receive a new linked version listing each other by name.

  INGREDIENT DROPS (currently dead-end):
    Kill specific mobs (Wither Skeleton, Creaking, Enderman in storms/warped
    forest, Guardian, Shulker) → chance to drop typed ingredient items
    (Volatile Bone, Shadow Heartwood, Void Chorus, Sentinel Eye, Fractured Echo).
    Players can pick these up, but NO game mechanic currently uses them.

A. WHAT PLAYERS CAN CURRENTLY DO
─────────────────────────────────
  ✓ Craft a Totem Altar via a shaped recipe (configurable).
  ✓ Place the altar in the world; receive placement particles, sound, and a
    floating hologram label.
  ✓ Kill hostile mobs to obtain Totem Shards (5% drop chance from any Monster).
  ✓ Morph a Totem Shard by killing the right type of mob while holding it
    (configurable mob-to-affinity mappings, configurable threshold).
  ✓ Watch the shard's lore update in real time showing affinity progress.
  ✓ Repair an inactive altar by inserting a Wither Skull and killing 25 ritual
    mobs; a boss bar and hologram track progress.
  ✓ Forge a morphed shard at a repaired altar to receive a typed Totem of Undying.
  ✓ Use Blast Totem on death: knockback ring + explosion effects.
  ✓ Use Shadow Totem on death: 15s invisibility + smoke particles.
  ✓ Use Storm Totem on death: random teleport 25–35 blocks away.
  ✓ Use Swap Totem on death: swap positions with a random nearby player.
  ✓ Use Guardian Totem on death: pull linked ally to your location (requires
    prior right-click linking ritual with another online player).
  ✓ Pick up ingredient drops (Volatile Bone, Shadow Heartwood, etc.) from
    specific mobs — but they have no in-game function yet.
  ✓ (Admin) Give shards, altars, and reload config via /totemaltars commands.


B. WHAT IS UNFINISHED
──────────────────────
  1. INGREDIENT SYSTEM — MOST CRITICAL GAP
     Five ingredient items drop from specific mobs with configurable chances.
     Their item lore says "Bring to a Totem Altar." No altar GUI slot accepts
     them, no code checks for them, no recipe uses them. The entire ingredient
     layer is a dead stub.

  2. ALTAR TYPE BINDING
     AltarManager has bindAltar(loc, type, owner), isBound(), getType().
     Config has messages: altar-bound-success, altar-already-bound,
     altar-not-bound, altar-requires-morphed-shard. Neither the method nor the
     messages are reachable from any code path. The intended design (inserting
     a morphed shard to "bind" the altar to one totem type permanently) is
     infrastructure-complete but logic-disconnected.

  3. ITEM MIGRATION STUB
     LegacyTotemUtil.migrateLegacyTotemIfSafe() returns false unconditionally.
     Players using items from plugin version ≤ 1.0.x may have
     AMETHYST_SHARD-based shards (migrateToEchoShard() handles this partially
     inside morphShard/updateShardLore, but there is no proactive migration pass
     on player join or inventory open).

  4. SHADOW ARMOR EFFECTS
     ShadowArmorManager.isInShadow() is defined but never called. The original
     design presumably involved hiding or swapping armor appearance during
     shadow mode (e.g., removing visible armor to enhance the stealth fantasy),
     but this was never implemented.

  5. BOSS BAR — CONFIG-DRIVEN MESSAGES
     RitualManager hardcodes "Repairing Altar: X / Y Souls" as the boss bar
     title — it is not read from config.yml messages unlike every other string
     in the plugin.

  6. RITUAL TIMEOUT / PERSISTENCE
     Active rituals exist only in memory. A server restart silently resets
     the ritual (altar stays damaged, mobs despawn, boss bar gone). No ritual
     timeout is implemented for AFK players.

  7. ALTAR OWNERSHIP ENFORCEMENT
     owner UUID is stored in altars.yml but is never checked. Any player can
     interact with, repair, or destroy any altar regardless of who placed it.

  8. PER-TYPE COOLDOWNS
     CooldownManager supports per-key cooldowns (arbitrary String key), but
     only the single "__global__" key is ever used.

  9. ADMIN TOOLING
     No list, inspect, or forcibly-remove commands for placed altars.
     No admin command to give a pre-morphed shard of a specific type.

  10. ALTAR-TYPE HOLOGRAM
      Hologram only shows INACTIVE / RITUAL / ACTIVE states. A bound altar
      (when binding is implemented) would ideally display its type prominently.


C. RECOMMENDED NEXT DEVELOPMENT PRIORITIES
────────────────────────────────────────────
  PRIORITY 1 — Wire up the ingredient system (high impact, mostly additive)
    Add an "ingredient slot" to the Forging GUI alongside the shard slot.
    Check that the ingredient type matches the shard type before forging.
    This completes the established loot-table promise to players.

  PRIORITY 2 — Implement altar type binding (completes the altar lifecycle)
    Call bindAltar() from AltarInteractionListener when a morphed shard is
    inserted into an active altar. After binding, the altar only accepts shards
    (and ingredients) of that type. Surface the bound type in the hologram.

  PRIORITY 3 — Boss bar message config key (small, polish)
    Move "Repairing Altar: {current} / {required} Souls" into config.yml
    messages under a new key (e.g., ritual-bossbar-format) and read it in
    RitualManager, consistent with all other strings.

  PRIORITY 4 — Implement shadow armor hiding (moderate, completes Shadow Totem)
    Use ShadowArmorManager.isInShadow() to hide armor during shadow mode
    (e.g., via ArmorEquipEvent interception or ArmorStand data, or simply
    sending empty equipment packets). This completes the existing stub.

  PRIORITY 5 — Ritual persistence across restarts (moderate complexity)
    Store active ritual state (kills so far) in altars.yml or a separate file.
    On server start, resume active rituals or at minimum log them as "interrupted"
    so the altar is not left in a permanently stuck state.

  PRIORITY 6 — Git version control (immediate, zero code change)
    The plugin has no git history. One rm command away from total loss.
    git init && git add . && git commit -m "v1.1.5 source baseline" — then
    push to GitHub/GitLab.

  PRIORITY 7 — Admin commands (quality of life for operators)
    /totemaltars list — shows all registered altars (world, coords, stage, type)
    /totemaltars inspect <x> <y> <z> — shows detailed altar state
    /totemaltars remove <x> <y> <z> — admin-force-remove an altar
    /totemaltars giveshard <player> <type> — give a pre-morphed shard

  PRIORITY 8 — Per-type cooldowns (gameplay depth)
    Use the existing CooldownManager key parameter to implement per-type
    cooldowns (e.g., blast: 30s, shadow: 60s, storm: 45s) in addition to or
    instead of the single global cooldown.
